# Требования к системе бронирования коворкинга

## 1. Роли пользователей

| Роль | Что делает | Доступ к данным |
|---|---|---|
| **Гость (guest)** | Просматривает каталог пространств (рабочие места, переговорные), доступность по датам. Не может бронировать. | Только чтение справочников `space`, `space_type`; не видит персональные данные пользователей и брони. |
| **Сотрудник (member)** | Бронирует пространства, просматривает свои брони, отменяет их в рамках правил. | Свои брони (`booking`), справочники пространств; не видит чужие брони и данные других пользователей. |
| **Администратор (admin)** | Управляет пространствами и типами, просматривает все брони, отменяет любые брони, формирует отчёты. | Все таблицы без ограничений; может изменять справочники и брони. |

## 2. Сценарии использования

### Сценарий 1: Успешное бронирование
**Роль:** сотрудник  
**Шаги:** 1) Выбирает пространство и интервал. 2) Система проверяет отсутствие пересечений. 3) Создаётся бронь со статусом `CONFIRMED`. 4) Пользователь видит подтверждение.  
**Результат:** запись в `booking` создана, конфликтов нет.  
**Граничный случай:** если интервал пересекается с существующей бронью — система возвращает ошибку, бронь не создаётся.

### Сценарий 2: Отмена брони сотрудником
**Роль:** сотрудник  
**Шаги:** 1) Открывает список своих броней. 2) Выбирает активную бронь. 3) Нажимает «Отменить». 4) Статус меняется на `CANCELLED`.  
**Результат:** бронь помечена как отменённая, интервал освобождается.  
**Граничный случай:** попытка отменить бронь, которая уже началась или завершилась, — отклоняется (проверка по времени).

### Сценарий 3: Просмотр доступности (гость)
**Роль:** гость  
**Шаги:** 1) Выбирает дату и тип пространства. 2) Система показывает свободные интервалы.  
**Результат:** список свободных слотов без раскрытия персональных данных.  
**Граничный случай:** если все пространства заняты — возвращается пустой список с корректным сообщением.

### Сценарий 4: Администратор создаёт новое пространство
**Роль:** администратор  
**Шаги:** 1) Вводит код, вместимость, тип. 2) Система проверяет уникальность кода и положительную вместимость. 3) Пространство сохраняется.  
**Результат:** запись в `space` создана.  
**Граничный случай:** попытка создать пространство с уже существующим кодом — ошибка уникальности.

### Сценарий 5: Двойная бронь (граничный)
**Роль:** сотрудник  
**Шаги:** 1) Два пользователя одновременно пытаются забронировать одно пространство на пересекающийся интервал. 2) Первая транзакция фиксируется. 3) Вторая получает ошибку нарушения exclusion constraint.  
**Результат:** создаётся только одна бронь; вторая отклоняется на уровне БД.  
**Граничный случай:** даже при одновременных запросах база гарантирует отсутствие пересечений.

### Сценарий 6: Отмена после начала (граничный)
**Роль:** сотрудник  
**Шаги:** 1) Пользователь пытается отменить бронь, время начала которой уже прошло. 2) Система проверяет `start_time > now()`.  
**Результат:** отмена запрещена.  
**Граничный случай:** если `start_time` равен текущему моменту — также считается начавшейся.

### Сценарий 7: Просроченная бронь (граничный)
**Роль:** система / администратор  
**Шаги:** 1) Бронь имеет статус `CONFIRMED`, но `end_time` уже прошёл. 2) Фоновая задача или администратор может перевести её в `EXPIRED`.  
**Результат:** статус обновлён, пространство считается свободным.  
**Граничный случай:** если бронь не была отменена и время вышло — она не должна блокировать новые брони на будущие интервалы.

## 3. Сущности и атрибуты

| Сущность | Атрибуты | Предполагаемый ключ | Тип ключа |
|---|---|---|---|
| **app_user** | `user_id` (PK), `email` (UNIQUE, NOT NULL), `full_name` (NOT NULL), `role` (NOT NULL, CHECK IN ('guest','member','admin')), `created_at` | `user_id` | суррогатный |
| **space_type** | `type_id` (PK), `name` (UNIQUE, NOT NULL), `description` | `type_id` | суррогатный |
| **space** | `space_id` (PK), `code` (UNIQUE, NOT NULL), `capacity` (NOT NULL, CHECK > 0), `type_id` (FK → space_type), `is_active` (DEFAULT true) | `space_id` | суррогатный |
| **booking** | `booking_id` (PK), `space_id` (FK → space), `user_id` (FK → app_user), `time_range` (tstzrange, NOT NULL), `status` (NOT NULL, CHECK IN ('CONFIRMED','CANCELLED','EXPIRED')), `created_at` | `booking_id` | суррогатный |

## 4. Связи и кардинальности

- **app_user (1) — (N) booking**: один пользователь может иметь много броней; бронь обязательно принадлежит одному пользователю.
- **space (1) — (N) booking**: одно пространство может быть забронировано много раз (в разные интервалы); бронь обязательно относится к одному пространству.
- **space_type (1) — (N) space**: один тип может объединять много пространств; каждое пространство имеет ровно один тип.

## 5. Бизнес-правила и ограничения

1. **Уникальность email пользователя**: `UNIQUE (email)`.
2. **Вместимость пространства положительна**: `CHECK (capacity > 0)`.
3. **Уникальность кода пространства**: `UNIQUE (code)`.
4. **Запрет пересечения активных броней одного пространства**: exclusion constraint на `booking` с условием `status = 'CONFIRMED'` — два активных бронирования одного пространства не могут пересекаться по времени.
5. **Статус брони только из допустимого набора**: `CHECK (status IN ('CONFIRMED','CANCELLED','EXPIRED'))`.
6. **Интервал брони непустой и корректный**: `CHECK (NOT isempty(time_range))` и `CHECK (lower(time_range) < upper(time_range))`.

## 6. Профиль нагрузки

| Тип | Операции | Ожидаемый объём |
|---|---|---|
| **OLTP** | Создание/отмена брони, проверка доступности, вход пользователя | Сотни–тысячи транзакций в день; строки в `booking` — десятки тысяч в год. |
| **OLAP** | Отчёты по загрузке пространств, популярные интервалы, активность пользователей | Агрегаты по `booking` за периоды; запросы с `GROUP BY`, `date_trunc`. Объём данных — до миллионов строк при росте. |

## 7. Нефункциональные требования

- **Доступность**: 99,5% в рабочее время.
- **RPO**: ≤ 15 минут (регулярные бэкапы / WAL-архивация).
- **RTO**: ≤ 1 час.
- **Безопасность**: аутентификация; разграничение доступа по ролям; сотрудник видит только свои брони (реализуется на уровне приложения или через RLS); персональные данные не раскрываются гостям.
